# Conflict evaluation v2

A held-out evaluation of how a memory store resolves new facts against old ones. It replaces the single 400-query workload as the basis for any claim about MemKit's conflict handling.

## Why a second evaluation

1. **The published staleness figure does not reproduce.** The earlier workload reported 52% stale for MemKit against 81% for vector retrieval. On a clean database the current code gets 21% (95% interval 17% to 25%), and replaying the same user's workload a second time on the same database gives 28%. The vector baseline did reproduce (80.5%). The earlier runner used one fixed user id against a database that persists, so repeated runs accumulated state. A probe query on an empty store now guards against this.
2. **The earlier workload had one conflict type.** Same subject, same attribute, same sentence frame, single-token values, adjacent in time, and it was reshaped after a smoke test against the system under test. It had no split between tuning and testing, no unrelated facts that must survive, and no measure of wrongly overwritten facts.

## Workload

Fully synthetic, deterministic, generated by `data/synthetic/generate_conflict_v2.py`. Each split has 102 query events in each of five categories.

| Category | What happens | Pass condition |
| --- | --- | --- |
| update same frame | Same person, same attribute, same sentence frame, new value of 2 to 3 tokens | new fact retrieved, old fact not retrieved |
| update reworded | Same person and attribute, new value in a different sentence form | same |
| other person, same value | Two people (some share a surname) state the same value | each person's fact still retrieved |
| other attribute | Same person states two different attributes | both facts still retrieved |
| restatement | The same fact repeated in other words | the fact is still retrieved |

A fact counts as stale if the old fact appears in the top 5 results. In the three survival categories a fact counts as lost if it is missing from the top 5 results for its own query. Most of these are supersessions, but a retrieval miss counts too. The vector baseline never supersedes anything, and it scores 0.0% to 1.0% lost, which bounds the retrieval-miss floor; the rest of any larger number is attributable to supersession. (The raw results files and the scorer call this metric `false_supersession_rate`.) The development and test splits share no attribute family, first or last name, value, value token, or sentence form; a test checks this. Three test families put the value before the subject.

## Protocol

1. All tuning used the development split only. Four configurations were tried (below).
2. Before seeing iteration 4, I declared a selection rule: choose the configuration with the lowest mean stale rate among those whose wrongful-supersession rate is at most 5% in all three survival categories, ties broken by latency. That rule selects iteration 3.
3. Iteration 4 misses the rule by 0.9 points in one category (5.9%, interval 3% to 12%), and its stale rate is far lower. I did not change the rule. Both configurations were run on the test split exactly once and both are reported.
4. Each run used a fresh database and a fresh user id. Model decoding used temperature 0. Each number is one run; the intervals are Wilson 95% intervals over 102 queries.

Disclosures:

- Before choosing the candidate count, I computed one text-only diagnostic on the test split (the rank of the true old fact under word overlap). It used no system output. The candidate count was chosen from development numbers, but the test split was not fully unseen by me.
- A first development run was discarded: I made probe writes into its evaluation user, and the host slept during it.
- The model is `llama3.1:8b` served by Ollama. Other models were not tried.
- The numbers above come from the revision before a hardening pass that followed an independent code review: prompt text is collapsed to one line and capped at 300 characters, a judge failure now stops the walk and adds the fact, every change to one user's memories is serialized, inserting the new fact and superseding the old one is one transaction conditional on the old fact still being active, resolutions in flight are bounded, a write stops waiting for the model after a time budget, and the response size is bounded. The prompt change alters none of the 1,632 facts in both splits (the longest is 80 characters), and the other changes act only on failures or on concurrent writes, so behavior on these runs should be identical. The test split was not rerun on the final revision.
- All 17,908 judge calls across every run returned HTTP 200. Whether any answer was unparseable (an invalid answer was handled differently in the earlier revision) was not recorded.
- A stored fact can still influence the judge, because the judge reads stored text. Collapsing it to one line stops it from imitating the prompt's structure but does not remove the influence. Supersession is reversible: the old fact is archived and kept until the retention window ends.
- Before a write is stored, a fact whose word overlap with an existing fact reaches 0.85 is treated as a duplicate without asking the judge. Two long sentences about different people that differ by one name can reach that overlap, so the new fact would not be stored. This is not covered by the evaluation.

## What the results show

- **Lost facts fell sharply and the gain held on unseen data.** With the current heuristic, another person's fact is missing from the top five 72% of the time and another attribute of the same person 50% of the time. With a local-model judge those are 8% and 4% (iteration 4), or 5% and 3% (iteration 3). The keep-everything baseline's 0% to 1% shows almost all of the heuristic's loss is supersession.
- **Stale answers did not improve in general.** On same-frame updates the heuristic is lower (15.7%) than iteration 4 (29.4%). The heuristic gets there by replacing facts indiscriminately, so only 69% of new facts remain retrievable, against 95% with the judge.
- **Latency is the price.** About 1.3 s per write for iteration 3 and 4.6 s for iteration 4, against 1.3 ms for the heuristic.
- **The limiting step is candidate search, not judgment.** The judge said "update" for 16 of 16 true old and new pairs I checked, and on development it fixed the same-frame case completely (0% stale). On the test split the true old fact is within the ten most word-similar candidates only 85% of the time for same-frame updates and 69% for reworded ones (text-only diagnostic), versus 99% and 93% on development. A fact the judge never sees cannot be superseded. Stale rates on the test split track that ceiling.
- **Not tested:** semantic candidate search (embeddings or similar), other judge models, real conversations, or MemKit's Claude-based resolver. That resolver's prompt has no subject check, so it may overwrite another person's fact; it was not evaluated here.

## Defects this evaluation found in MemKit

- A search containing `?` or any other punctuation returned HTTP 500, because the text was passed to SQLite's full-text syntax unescaped. Fixed: every non-alphanumeric character is a separator and each token is quoted.
- A search with no results returned `null` instead of `[]`. Fixed.

## Reproduce

```bash
go build -o memkit ./cmd/memkit
MEMKIT_RESOLVER=ollama MEMKIT_OLLAMA_MODE=pair MEMKIT_OLLAMA_URL=http://127.0.0.1:11434 \
  MEMKIT_DB=/tmp/eval.db MEMKIT_ADDR=:8098 ./memkit
cd eval
python scripts/run_conflict_v2.py --split dev --backend memkit --memkit-url http://localhost:8098
python scripts/run_conflict_v2.py --split test --backend vector
```

Hold the machine awake for long runs (for example `caffeinate -ims`). A full split takes about an hour in pair mode.
